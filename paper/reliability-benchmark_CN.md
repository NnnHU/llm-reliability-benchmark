# 结构化任务分解提升基于 LLM 的知识分析可靠性
(*Structured Task Decomposition Improves Reliability of LLM-Based Knowledge Analysis*)

**工程实验报告**

> 一项可复现的基准测试，针对结构化知识分析任务比较了五种执行策略 ——
> 单次调用、重试、单模型流水线、多模型 Panel+Judge 以及单模型自我批判 ——
> 测试语料为 13 个用例。核心发现：将任务分解为「抽取 → 分析 → 判定」(extract → analyze → judge)
> 可将返回有效结构化输出的成功率从约 31% 提升至约 92%，
> 并且这一增益来源于分解本身，而非重试。

---

## 摘要

大语言模型在被要求于单次调用中产出结构化分析输出时，常常会"静默失败"：
返回空响应、无法解析的文本，或拒绝执行任务。我们在固定的 13 例金融文档语料上
比较了复杂度递增的五种执行策略，在可能的情况下保持模型不变，以隔离每种策略的贡献。
我们发现：(1) **任务分解**(抽取 → 分析 → 判定的流水线)是可靠性的主导驱动因素，
将成功率从 31%(单次调用)提升至 92%，而单纯重试仅带来 +8 个百分点；
(2) 在盲评双 LLM 评分并以人工锚点校验的条件下，**多模型 Panel+Judge** 架构
在准确率、覆盖率、整体质量与幻觉率上均优于单模型流水线。我们发布了
完整的基准测试框架、语料与执行轨迹，以便复现结果并将其扩展至其他领域。

---

## 1. 引言

在使用 LLM 时一种常见的工程体验：你请求一份结构化的 JSON 分析，
模型却返回空内容、拒绝，或是没有任何 JSON 的散文。对于玩具任务这不过是麻烦；
但对于必须返回可靠结构化输出的产品而言，这是致命的。

两种直观的修复方法常被尝试：**失败后重试**，以及**加入更多模型**(即"混合专家/MoA")。
两者听起来都合理，但在没有对照实验的情况下，并不清楚哪一种真正能带来可靠性 ——
以及代价几何。

本报告描述了一个旨在**隔离每个因素贡献**的基准测试。我们定义了五种执行策略(§3)，
它们构成一条单变量变更的链，在共享语料上运行，并测量**可靠性**(是否返回了
有效的结构化输出？)与**质量**(该输出是否够好？)。该设计使我们能够把增益归因于
具体的机制，而非"使用了更花哨的设置"。

---

## 2. 实验设置

### 2.1 五种执行策略

每种策略针对同一份源文档回答同一问题，并产出相同的目标结构
(一个四字段的判定结果：共识 / 分歧 / 盲点 / 判定)。它们仅在*工作组织方式*上有所不同。

| 模式 | 功能 | 代价(API 调用) | 隔离 |
|---|---|---|---|
| **M1** 单次调用 | 一次调用；prompt 中包含文档与问题 | 1 | 基线 |
| **M1R** 单次 + 重试 | 同 M1，但在输出为空 / 错误时重试(≤4 次) | 1–4 | 单纯**重试**的贡献 |
| **M2** 单模型流水线 | 抽取 → 分析 → 判定，全程使用同一模型 | 3 | 在重试之外**任务分解**的贡献 |
| **M3** 多模型 Panel+Judge | 抽取后，由 2 个模型并行分析，再由 Judge 综合 | 4 | 在单模型流水线之外**多模型**的贡献 |
| **M4** 单模型自我批判 | 回答 → 批判 → 修订，单模型 | 3 | **自我反思**是否可媲美多模型 |

该链条的设计使得每一步**理想情况下只变更一个变量**：

```
M1 → M1R   : +重试，其余不变           (重试的贡献)
M1R → M2   : +流水线结构            (分解的贡献)
M2 → M3    : +面板中的第二个模型   (多模型的贡献)
M4 ↔ M3    : 自我批判 vs 多模型   (自我反思是否足够？)
```

存在一个残留的混杂变量(见 §5)：M3 的 Judge 接收两份分析，而 M2 的 Judge 只接收一份，
因此"模型数量"与"Judge 输入丰富度"未完全分离。我们如实报告此点，而非过度声称。

### 2.2 语料

13 个用例，全部来自同一金融投资系列文章(Jeremy Grantham / GMO 的泡沫叙事)，
选择依据是叙事丰富度以及存在具体可核实的事实(日期、市盈率、资产管理规模 AUM 数据)。
组成如下：

- 1 份英文摘要文档(约 3.3k 字符)
- 7 份标准中文(繁体)ASR 转录稿(每份约 9–12k 字符；
  含语音转文字噪声 —— 错字、误听人名)
- 3 份大型文档(约 31–34k 字符)
- 1 份超大型文档(约 53k 字符)
- 1 个多文档用例(3 份文档拼接，约 32k 字符)

总计：约 256k 字符。ASR 噪声是有意为之 —— 它检验对真实杂乱输入的鲁棒性。
语料在领域上较窄(金融)；这是一个已知局限(§5)。

### 2.3 模型

- Panel / Judge：`deepseek-v4-flash`(经 `api.deepseek.com`，OpenAI 兼容协议)
- 第二个面板模型：`deepseek-v4-pro`
- 温度：分析 / 判定阶段为 0.7，抽取阶段为 0.5，批判阶段为 0.5
- 每次调用最大 token 数：2048；超时：360s

### 2.4 指标

**可靠性**(全部 13 例、5 种模式)：当且仅当某一模式返回了四个判定字段的**真实**内容时，
即视为在该用例上"成功" —— 解析回退占位符如 `"(could not parse ...)"` **不**计入。
(本分析的一份早期草稿曾错误地将占位符计为成功；该缺陷已被发现，
以下数据为修正后的结果。见 §5 关于方法论的说明。)

**质量**(在 M2 与 M3 均产出真实输出的 7 个用例上)：由**两个独立的 LLM 评分者**
(Gemini 与 KIMI K2.6)在**盲评 A/B 设计**下打分 —— 两名评分者均不知道哪份输出是 M2
或 M3。位置偏差通过对每个用例进行 A/B 顺序重排予以消除。一名**人工锚点**盲评了
3 个用例以校验 LLM 评分者。评分量表：事实准确率(1–5)、幻觉(Y/N)、关键信息覆盖率(1–5)、
整体质量(1–5)，以及一次强制偏好选择(A / B / 平局)。

## 3. 结果

### 3.1 可靠性 —— 分解而非重试驱动成功

| 模式 | 成功率 | 平均延迟 | 平均输出字符数 | API 调用数 |
|---|---|---|---|---|
| M1 单次调用 | **31%** (4/13) | 21.4s | 458 | 13 |
| M1R 单次 + 重试 | **38%** (5/13) | 45.7s | 626 | 21 |
| M2 单模型流水线 | **92%** (12/13) | 55.3s | 1,339 | 39 |
| M3 多模型 Panel+Judge | **92%** (12/13) | 50.4s | 1,531 | 52 |
| M4 单模型自我批判 | **38%** (5/13) | 74.2s | 899 | 39 |

**解读链条：**

- **M1 → M1R：+8 个百分点。** 重试仅挽救了 9 次失败中的 1 次。空响应问题
  并非一次第二次尝试就能修复的瞬时抖动 —— 在约 60% 的情况下，模型确实难以
  应对单次结构化 JSON prompt。**单纯重试是不够的。**

- **M1R → M2：+54 个百分点。** 将任务分解为抽取 → 分析 → 判定
  (使用同一单模型)将可靠性从 38% 提升至 92%。这是主导效应。
  **任务分解 —— 而非重试 —— 才是使流水线可靠的关键。**

- **M2 → M3：可靠性上 +0 个百分点**(均为 92%)，但请见质量(§3.2)。
  一旦流水线就位，加入第二个模型并不会进一步提升产出有效输出的*比率*。

- **M4(自我批判)：38%。** 单模型对其自身输出进行批判与修订**并未**逼近
  流水线的可靠性。这是一种朴素的回答→批判→修订实现；经工程化设计的自我反思
  (Reflexion、Self-Refine、Constitutional AI)或许能做得更好 —— 但结果表明
  自我批判并非分解的天然替代品。

> **核心发现：** *结构化任务分解显著提升了基于 LLM 的结构化分析的可靠性 ——
> 从约 31% 提升至约 92%。该增益来自分解本身，而非重试。*

### 3.2 质量 —— 多模型胜过单模型流水线(盲评、双 LLM + 人工锚点)

对于 M2 与 M3 均返回真实分析的 7 个用例，由 Gemini + KIMI K2.6 盲评打分
(共 14 票)：

| 指标 | M2(单模型流水线) | M3(多模型 Panel+Judge) | Δ (M3 − M2) |
|---|---|---|---|
| 事实准确率(1–5) | 3.14 | **4.14** | **+1.00** |
| 关键信息覆盖率(1–5) | 2.93 | **3.79** | **+0.86** |
| 整体质量(1–5) | 2.86 | **3.71** | **+0.86** |
| 幻觉(计数 /14) | 3 | **2** | M3 更少 |
| 偏好胜出(共 14 票) | 6 | **8** | M3 胜出 |

**最强的单一信号：两名 LLM 评分者在 7/7 个用例(100% 评分者间一致性)上
偏好一致。** 两个架构上不同的模型，独立且在盲评条件下打分，每次都选出同一胜者 ——
这很难出于巧合，表明 M2 与 M3 的差异是一个真实信号，而非评分尺度噪声。

**人工锚点校验：3/3 一致。** 一位具备领域知识的人类盲评了 3 个代表性用例
(刻意包含 2 个 LLM 选择单模型 M2 的用例 —— 即反直觉选择)。该人类在全部 3 例上
与 LLM 评分者一致，包括两例 M2 胜出。这证实 LLM 评分者并非盲目偏向多模型：
当单模型确实更好时它们会选择单模型，而人类也认同。

**解读：** 当两种模式都成功时，多模型 Panel+Judge 产出的输出质量**更高** ——
更准确、覆盖率更好、幻觉更少，且更常被偏好。先前"M2 ≈ M3"的表象(源于输出字符计数)
是一种测量假象：按丰富度代理指标看它们似乎相当，但在真实质量评分下
多模型领先。

### 3.3 值得关注的次要发现

- **并行性抵消了延迟。** M3(4 次调用，2 个模型并行)平均耗时 50.4s，
  而 M2(3 次串行调用)为 55.3s。此处多模型扇出**并不**消耗实际墙钟时间，
  尽管它消耗约 33% 更多的 token。
- **M3 在 6/13 个用例上延迟优于 M2**，包括多文档用例
  (M2 101s 对 M3 37s)，在该用例中，单模型上的串行抽取 → 分析 → 判定
  比并行面板更慢。

## 4. 可复现性

该基准测试可从 commit `9301168` 的代码库完整复现。

```bash
# 在全部 13 个用例上运行全部 5 种模式(约 40–70 分钟，约 150 次 API 调用)
npm run bench -- --full

# 增量运行：仅运行 M1R + M4，合并先前的 M1/M2/M3 轨迹
npm run bench

# 仅重跑 M2 + M3(例如在修复抽取重试问题之后)
npm run bench -- --remediate
```

**语料：** `bench-samples/`(13 个用例 + `samples.json` 清单)。语料领域
较窄(金融)；用其他领域的文档替换它即可检验泛化能力。

**配置：** `.env`，含 `VITE_VERDEX_PROVIDER_*` 与
`VITE_VERDEX_PROVIDER2_*`(两个 OpenAI 兼容的提供方)。

**输出：** `bench-results/`(已 gitignore —— 含真实模型输出)：
- `<runId>-<case>-<query>-trace.json` —— 全保真轨迹(未截断)
- `<runId>-<case>-<query>-report.md` —— 每用例对比表
- `<runId>-SUMMARY.md` —— 汇总与关键问题分析

**盲评质量评分包：** `npx tsx scripts/extract-grading.ts`
生成每个用例的 A/B 文件(`bench-results/grading-pack/`)，供任意 LLM 或人类
盲评打分。A/B → 模式的映射保存在 `quality-grading-key.json` 中
(评分完成前保密)。

## 5. 讨论

### 5.1 证据所支持的内容

- **强有力的：** 任务分解提升可靠性(31% → 92%，n=13，干净地分离了
  重试与分解)。
- **初步但一致的：** 多模型 Panel+Judge 在质量上优于单模型流水线
  (5 项指标，n=7，双 LLM 7/7 一致，人工锚点 3/3)。我们将其表述为
  *"证据一致地支持"*，而非*"证明"* —— n=7 与单一领域并非普适证明。

### 5.2 局限

- **样本量。** 可靠性 n=13，质量 n=7。方向性结论，并非统计上确定。
- **领域狭窄。** 所有用例均为金融投资文本。分解效应是否跨领域
  (代码、法律、医学)成立，尚未检验。语料被设计为可替换以检验此点。
- **M2 与 M3 之间存在一个残留混杂变量。** M3 的 Judge 接收两份分析，
  而 M2 的 Judge 只接收一份，因此"模型数量"与"Judge 输入丰富度"协变。
  结果应解读为"多模型 Panel+Judge > 单模型流水线"，
  而非"仅凭更多模型 > 仅凭更少模型"。一个完全隔离的测试应
  向 M2 的 Judge 喂入同一份单模型分析的两份副本。
- **M2 的低分部分由抽取驱动。** 在 2–3 个用例中，M2 的抽取步骤即使
  重试后仍部分失败，致使其质量分数向下偏倚。在干净的用例上方向
  (M3 > M2)同样成立，但差距幅度可能被放大。
- **LLM 评分者，而非仅人类。** 人工锚点(3 个用例)校验了 LLM 评分者的
  方向，但更大规模的人类研究会增强这一结论。

### 5.3 方法学说明：占位符缺陷

本分析的一份早期草稿曾报告每种模式"100% 成功"。那是一个统计缺陷：
解析器在失败时会发出非空的占位符字符串
(`"(could not parse ...)"`)，而一次朴素的非空检查将它们计为成功。
该缺陷是在察觉数据看起来异常干净时被发现的，修复
(将占位符排除出成功标准)后即得到 §3 中的数据。我们将此故事保留在
报告中，因为捕捉并纠正自身的测量偏差是可信基准测试的核心部分 ——
也提醒我们：*最危险的失败，是那些看起来像成功的失败。*

### 5.4 对实践的启示

对于构建必须返回可靠结构化输出的 LLM 产品的团队：

1. **先做分解。** 在加入更多模型或更花哨的 prompt 之前，先把任务拆分为
   抽取 → 分析 → 判定。在我们的基准测试中，这一项改变的效果最大。
2. **重试是廉价的保险，但不是修复手段。** 加上它，但不要指望它
   解决一个本质上困难的一次性 prompt。
3. **多模型在质量上而非可靠性上回本。** 一旦流水线可靠，第二个模型即可
   提升输出质量(准确率、覆盖率、幻觉)而不增加延迟
   (并行性抵消了它)。
4. **自我批判并非免费替代品。** 一个朴素的回答→批判→修订循环
   未能匹敌流水线。若要追求自我反思，请使用工程化的 prompt
   (Reflexion 风格)，并对其进行基准测试。

## 6. 相关工作

- **Self-Refine / Reflexion / Constitutional AI** —— 单模型自我改进循环。
  我们的 M4 是其朴素实例；经工程化设计的变体可能优于它。基准测试的
  M4 插槽正是此类方法可插入对比之处。
- **Mixture-of-Agents(MoA)** —— 多模型聚合。我们的 M3 是一个最小化的
  MoA(2 个面板 + 1 个判定)。基准测试通过与之对比 M2(单模型流水线)
  来隔离 MoA 的贡献。
- **LLM-as-judge / 人工锚点评估** —— 我们采用双 LLM 盲评加人工锚点，
  遵循在无法开展完整人类研究时进行可信评估的新兴最佳实践。

## 附录 B：盲评评分协议

1. 对于 M2 与 M3 均产出真实输出的 7 个用例中的每一个，将四字段判定结果
   抽取至一份用例文件，并以稳定的带种子洗牌方式赋予 A/B 标签
   (映射保存至 `quality-grading-key.json`，评分期间保密)。
2. 每份用例文件包含：源文档、问题、输出 A、输出 B，
   以及一份评分量表。
3. 将每份用例文件独立喂给两名 LLM 评分者(Gemini、KIMI K2.6)。
4. 为消除位置偏差，两名评分者对每个用例接收不同的 A/B 顺序
   (框架按每用例种子变化顺序)。
5. 从每名评分者收集准确率 / 幻觉 / 覆盖率 / 整体分数 + 一次强制偏好。
6. **人工锚点：** 一名人类使用相同的盲评文件对 3 个用例打分
   (选择时纳入 M2 胜出与 M3 胜出的用例)，随后将人类的偏好
   与 LLM 评分者进行一致性比对。
7. 揭盲：通过密钥文件将 A/B 映射回 M2/M3 并汇总。
